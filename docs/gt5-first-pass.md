# GT5 first semantic lowering pass

The first concrete `minecraft-redox` lowering target is the old GT recipe/material builder idiom. This is intentionally narrower than "translate GT5": it proves that Java which is structurally declarative can be recovered as content without pretending nested Java expressions have already been semantically resolved.

## Pipeline

```text
Java source
  -> tree-sitter syntax tree
  -> declaration inventory + import/static-import bindings
  -> receiver-oriented call chains
  -> GTNH recognizers
  -> recipe/material content records with exact source provenance
```

The Java frontend records only the calls along a receiver chain. Calls nested inside arguments remain arguments rather than being incorrectly folded into the builder chain. Imported types and explicitly statically imported members get stable qualified identities where possible.

For example:

```java
GTValues.RA.stdBuilder()
    .itemInputs(GTOreDictUnificator.get(OrePrefixes.dust, Materials.Netherrack, 4))
    .itemOutputs(GTOreDictUnificator.get(new ItemStack(Blocks.netherrack, 3)))
    .duration(5 * SECONDS)
    .eut(2)
    .addTo(compressorRecipes);
```

is recovered as a recipe whose builder is `gregtech.api.enums.GTValues.RA` and whose target map is `gregtech.api.recipe.RecipeMaps.compressorRecipes`, while inputs, outputs, duration and EU/t still retain their source expressions for later expression/type lowering.

## 2026-10-22 GT5-Unofficial measurement

A full scan of `GT5-Unofficial/src/main/java` sees:

- 3,374 Java files
- 191,679 outer receiver call chains
- 5,791 `GTValues.RA.stdBuilder()` recipe definitions
- 885 `new MaterialBuilder()...constructMaterial()` material definitions
- all 5,791 recipe builder chains structurally normalized
- all 885 material builder chains structurally normalized
- one Java file with a tree-sitter parse error (reported explicitly by the CLI): `kubatech/api/enums/ItemList.java`; inspection shows the source itself contains the invalid enum token sequence `ElectrodeDetectorHatch,;`

"Builder structurally normalized" means every call on that recognized builder chain has an accounted-for place in the recovered record. It does **not** mean expressions such as `GTOreDictUnificator.get(...)`, `15 * SECONDS`, lambdas, or arbitrary helper calls have already been resolved to final semantic IR.

That distinction is intentional. The Java frontend now also preserves a generic expression IR for references, literals, receiver calls, constructors, binary expressions and parenthesized expressions, with a raw fallback. The next layer is GT-specific expression/symbol/type lowering over that structure, not an optimistic parity claim.

The release-mode summary scan was initially single-threaded at 14.92 s / ~19 MB RSS. Parallel per-file analysis with deterministic summary reduction brings the same corpus to **2.12 s**, ~484% CPU and ~81 MB RSS on the Acer development host.

## Current recipe fields

The recipe recognizer currently separates:

- item/fluid inputs and outputs
- input/output chances
- duration
- EU/t
- special value / special item
- metadata/category
- cleanroom, low-gravity, buffering, NBT and other modifiers
- unsafe-item-input marker while still recovering the inputs themselves
- target recipe map
- post-`addTo` operations, kept distinct from builder semantics
- any still-unhandled builder calls (currently none in the measured GT5 source tree)

## Current material fields

Frequently queried material properties (name, display name, icon set, color, melting point, blast-furnace temperature) have dedicated fields. The rest of the known `MaterialBuilder` vocabulary is preserved as typed builder properties with arguments and provenance, including item forms, ore prefixes/byproducts, aspects/subtags, fuel/tool data, smelting relations, autogenerated recipe flags, enchantments, density, radioactivity-related properties, etc.

This is the first boundary where the old observation "a large fraction of GTNH is data cosplaying as Java" becomes executable rather than anecdotal.

## Expression semantics pass

The next layer keeps every original Java expression and its generic Java expression tree, then attaches a GT semantic interpretation only when a known construct is proven. Current recognized families include ore-dictionary forms (including named queries and unification wrappers), `ItemList` accessors, material item accessors, mod-item helpers, direct `ItemStack`/`OreDictItemStack` construction, `GTUtility.copyAmount*`, material/fluid accessors, direct `FluidStack`, and registry fluid helpers.

Duration arithmetic is evaluated only through exact integer operations and known **time-domain** constants (`GTRecipeBuilder` and `TickTime`). Volume constants such as `INGOTS` are deliberately not accepted as time merely because they are integers.

On the initial expression-only pass, before project-level method/type linkage:

- item expressions: 17,310 total; **14,546 semantically recognized (84.0%)**
- fluid expressions: 6,584 total; **6,266 semantically recognized (95.2%)**
- recipe durations: 5,748 total; **5,428 exactly reduced to integer ticks (94.4%)**

The unresolved tail is intentionally preserved. A major remaining item family is local helper calls such as `get(...)` in `ComponentAssemblyLineLoader`; their meaning comes from actual local method definitions, so resolving them belongs in a project symbol/method layer rather than a name-based heuristic.

## Project method index

The Java frontend now inventories method owners, return types, parameters, varargs/static status and exact provenance, and builds a compact project index. GTNH lowering runs as two parallel passes: one builds the method index; the second performs semantic recovery with that index available.

Local calls are linked only when `(source file, method name, arity)` identifies exactly one compatible method. Ambiguous overloads remain unresolved. A linked method returning `ItemStack` is recorded as a `LinkedMethod` semantic with its stable signature, but is **not** counted as a fully resolved item meaning until its body is understood.

On GT5 this links 431 recipe item expressions while preserving the previous 14,546 directly understood item semantics. `ComponentAssemblyLineLoader` accounts for 421 of those links: 299 calls to `get(OrePrefixes,Object,int)` and 122 calls to `get(ItemList,int)`. This is the intended handoff to method-body lowering rather than another name heuristic.

### Method return IR and safe inlining

Indexed Java methods now retain generic IR for their return expressions. For an unambiguous local call with exactly one return, minecraft-redox binds actual arguments to formal parameters, substitutes those references in the return expression, and feeds the substituted expression back through the ordinary semantic recognizers.

This is deliberately much weaker than arbitrary Java inlining: nested lambda/type returns are excluded, varargs are not substituted, and multi-return methods remain linked rather than guessed. On GT5 this converts 132 of the 431 linked item helpers into directly recovered semantics. The remaining 299 links are the branchy `ComponentAssemblyLineLoader#get(OrePrefixes,Object,int)` calls and stay explicit until control-flow/type evidence can determine their outcomes.

### Receiver type linkage

The project index now has owner and source-path method indexes over one shared method store, plus lexical receiver typing for method parameters and local variables. An unresolved call such as `werkstoff.get(...)` can therefore be linked through the enclosing method's declared parameter type to the actual overload, with ambiguity still causing a clean refusal.

Field access is now structural Java IR rather than a flattened source string. Field declarations are indexed with owner, declared type, static/instance status and provenance. Call resolution can therefore walk chains such as `MaterialsElements.getInstance().RUTHENIUM.getDust(64)` as: unique static method -> declared return type -> unique instance field -> declared field type -> unique instance method. Direct class calls such as `Particle.getBaseParticle(...)` are linked through imports and static method ownership. Static/instance mismatches and same-arity overload ambiguity remain hard failures rather than guesses.

The index stores each method/field once and keeps integer secondary indexes by source path and owner. After removing the earlier duplicated method storage, the two-pass GT5 scan remains fast enough to use interactively.

Latest GT5 measurement after receiver/field linkage:

- item expressions: 17,310 total; **14,679 directly recognized (84.8%) + 1,507 unambiguous method links = 16,186 accounted (93.5%)**
- fluid expressions: 6,584 total; **6,249 directly recognized (94.9%) + 208 unambiguous method links = 6,457 accounted (98.1%)**
- recipe durations: 5,748 total; **5,428 exactly reduced to integer ticks (94.4%)**
- release-mode two-pass scan: **2.92 s**, ~811% CPU, ~187 MB RSS on the Acer development host

The lower direct-fluid count versus the earlier 6,266 is an intentional accounting correction, not lost coverage: 17 dynamic `getInstance().FIELD.getFluid*` expressions had previously been accepted merely because their method names looked fluid-like. They are now part of the method-link bucket, backed by actual owner/field/return-type evidence. The link bucket also captures 78 `GTModHandler#getDistilledWater(long)`, 56 `SubstituteFluidStack#soldering(long)`, 28 `GTModHandler#getIC2Coolant(long)`, and 17 `Material#getFluidStack(int)` calls.

The largest item-link families are currently the branchy Component Assembly Line helper (299 calls), `Werkstoff#get(prefix, amount)` (260), `ItemRefer#get(int)` (255), `Werkstoff#get(prefix)` (155), `Material#getDust(int)` (97), `Particle#getBaseParticle(Particle)` (71), and `Particle#getIon(String,int)` (20). The completely unresolved item tail is down to 1,124 expressions (6.5%) and is now dominated by runtime `ItemStack` variables, Java arrays/alternative-input records, and a much smaller set of non-indexed or still-ambiguous calls rather than generic recipe-builder syntax.

Ordinary Java value lookup now also checks fields on the enclosing owner after locals and parameters, explicit/static-wildcard imported fields, and enum constants as implicit static values of their enum type. On GT5 this raises item method links from 1,507 to **1,752**, for **16,431 / 17,310 item expressions accounted (94.9%)**, without increasing the direct-semantic bucket. This closes a language-resolution gap for patterns such as class members, imported registries and `ComponentType.Electric_Motor...` without introducing GT-specific receiver-name rules.

### Structured recipe input arrays

Java array creation and array access are now structural expression IR. GTNH lowering assigns extra meaning only at the `itemInputs` boundary where `GTRecipeBuilder` itself defines the grammar: a two-element `Object[]` is an ore-dictionary alternative key plus amount, while an `ItemStack[]` is an explicit set of alternative stacks. The same array expressions outside recipe-input context remain plain Java arrays.

A pre-pass census found 210 unresolved raw item expressions, of which 137 were `new Object[]` alternative records and 24 were `new ItemStack[]` alternative arrays. After structural array lowering, direct item semantics rise from 14,679 to **14,840**, method links rise from 1,752 to **1,759** (array-access typing exposes a few more receivers), and total item accounting reaches **16,599 / 17,310 (95.9%)**. Fluid and duration accounting are unchanged. The completely unresolved tail falls to **711 expressions**: 405 plain references, 235 calls, 30 still-raw expressions, 19 array accesses, 18 field accesses and 4 parenthesized forms. At this point the dominant missing capability is value/dataflow recovery rather than syntax recognition.

### Parameterized recipe values and parser hygiene

Unresolved bare references are now linked to lexical Java values when the declaration proves an `ItemStack`-typed parameter, local or field. The resulting `LinkedValue` record carries a stable value ID, value kind and declared type; it is counted separately from both concrete item semantics and linked method results. This represents recipe templates such as `registerOre(..., ItemStack aStack)` without pretending `aStack` is a concrete item identity.

The Java frontend also now excludes line/block comments from argument lists and array initializers. Tree-sitter exposes comments as named children, so the earlier generic argument collector had counted 16 comments as item expressions and 2 as fluid expressions. Correcting that bookkeeping changes the GT5 denominators without changing any real recipe semantics.

- parameter/local/field item value links: **341**
- total item accounting: **16,940 / 17,294 (98.0%)**
- fluid expressions: **6,582 total**; 6,249 direct + 208 method-linked
- recipe durations: 5,748 total; 5,428 exactly reduced to ticks
- release two-pass scan: **2.94 s**, ~807% CPU, ~193 MB RSS on Acer

Only **354 item expressions** remain completely unexplained after this pass. The remaining tail is now dominated by calls whose semantics/types require more than owner/name/arity, plus a small number of non-`ItemStack` references, array accesses, field accesses and conditional expressions.

### Typed expression links and ordinary Java scope completion

The project index now carries enough Java type structure to account for additional expressions without pretending their concrete runtime values are known. Standard `Collection.toArray(T[])` calls inherit the supplied array type, so values such as `List<ItemStack>.toArray(new ItemStack[0])` become `TypedExpression(ItemStack[])`. Array-returning local helpers used inside multi-argument `itemInputs(...)` calls can be safely inlined back through the GT recipe-input grammar; the single-array-varargs case remains distinct so an `ItemStack[]` passed as the entire varargs array is not mislabeled as one alternative-input slot.

Nested Java owners are canonicalized with their full enclosing type chain, so references such as `MaterialsElements.STANDALONE.ADVANCED_NITINOL...` resolve through `package.Outer.Inner` rather than an invented top-level `package.Inner`. Constructors are indexed as `<init>` callable scopes for parameter/local lookup without becoming ordinary callable methods. Enhanced-for loop variables are given their lexical body scope, and direct `var x = new Type(...)` declarations infer the constructor type without any control-flow speculation.

These remain separate evidence classes:

- direct semantics mean the old recipe value itself has been understood;
- `LinkedMethod` means a unique Java method target and return type are known;
- `LinkedValue` means a unique parameter/local/field declaration and type are known;
- `TypedExpression` means the expression type is proven even though its runtime contents are not.

- fluid expressions: **6,582 total**; 6,249 direct + 208 method-linked

The remaining 157 item expressions are no longer a broad syntax problem. They are mostly genuinely dynamic calls, conditional expressions, external-library behavior, or cases that require stronger overload/control-flow evidence. Further percentage-chasing is therefore lower value than making the recovered semantics compile against a real Oxidized target IR with provenance and tests.


## Target content IR v1

The first source-language-free recipe target now exists in `minecraft-redox-core::content`. It deliberately contains no Java expression nodes: logical content IDs, named/material-form/ore-key item selectors, concrete stack amounts, input alternatives, recipe-map ID, duration ticks, EU/t and source provenance.

GTNH recipe lowering is fail-closed. A recovered builder only becomes a `ContentRecipe` when every semantic feature used by that source recipe is representable in target IR v1. Fluids, chances, metadata, modifiers, special values/items, post-`addTo` behavior, unresolved item selectors/amounts, missing duration and non-constant EU/t are explicit lowering blockers rather than silently discarded behavior.

This introduces the first real **generated/lowered** metric, distinct from parser/classifier coverage. On the full GT5 tree:

- recovered recipe builders: **5,791**
- recipe builders structurally normalized: **5,791**
- item expressions archaeologically accounted: **17,137 / 17,294 (99.09%)**
- recipes actually lowered into target content IR v1: **161 / 5,791 (2.78%)**

Per-recipe blocker counts (a recipe may have more than one blocker):

- non-constant EU/t: **4,634**
- fluids: **3,558**
- item input not yet concretely lowerable: **2,992**
- modifiers: **2,496**
- item output not yet concretely lowerable: **2,379**
- metadata: **1,156**
- chances: **418**
- missing duration: **363**
- missing EU/t: **55**
- special item/value: **31**
- post-add or otherwise unhandled builder behavior: **7**

The important result is not that v1 lowers only 161 recipes; it is that those 161 are the first recipes for which the compiler can make a much stronger claim: the output is a typed, source-language-independent content record and no unsupported source behavior was knowingly dropped.

The largest artificial blocker is now scalar evaluation rather than recipe syntax: 4,634 recipes use symbolic EU/t expressions such as tier constants instead of literal integers. Resolving statically provable GT tier constants is therefore the next high-leverage lowering pass, followed by explicit fluid IR rather than another round of syntax-percentage chasing.

### Source-backed scalar constant evaluation

EU/t lowering now runs through project-level Java constant evidence before target lowering. Static field declarations retain initializer IR and source provenance, source-path bindings are indexed once per file, numeric casts are structural expressions, and scalar evaluation follows static-final references, arithmetic, array access and standard integer extrema with cycle/depth guards.

`GTValues.VP` is the one GT-specific scalar transform in this pass. It is not a hard-coded voltage table: the evaluator only treats it as the practical-voltage array when the indexed `VP` initializer matches GT5's source pipeline `Arrays.stream(V).map(... * 30 / 32 ...).toArray()`. It then evaluates the sibling `V` array and `VoltageIndex` constants from source. Thus expressions such as `TierEU.RECIPE_HV / 2` derive their values through the declaration graph rather than by recipe-name heuristics.

Full GT5 result after this pass:

- target recipes lowered: **387 / 5,791 (6.68%)**, up from 161;
- non-constant EU/t blockers: **417**, down from 4,634;
- therefore **4,217** previously non-constant EU/t expressions are now statically resolved;
- the stricter recipe count rises by 226 because many recipes whose EU/t is now known still have independent blockers.

The dominant target-v1 blocker is now fluids at 3,558 recipes, followed by item inputs (2,992), modifiers (2,496), item outputs (2,379), and metadata (1,156). This makes explicit fluid content IR the next high-leverage target feature; chasing the remaining 417 dynamic/non-constant EU/t cases is lower value.

### Fluid target IR

Target content now includes source-independent `FluidSelector` and `FluidStackSpec` types plus fluid inputs/outputs on `ContentRecipe`. The core model has no Forge `FluidStack`, registry object, or Java accessor representation: fluids are either named logical IDs or material+fluid-form selectors.

The GTNH adapter lowers the dominant direct fluid families:

- material accessors such as `getFluid`, `getMolten`, `getGas`, `getFluidOrGas`, `getFluidStack`, and `getPlasma` to semantic forms (`fluid`, `molten`, `gas`, `fluid_or_gas`, `plasma`);
- direct `new FluidStack(...)` when the fluid identity is statically nameable;
- `FluidRegistry.getFluidStack("name", amount)` to named fluid content;
- fluid amounts through the same source-backed scalar evaluator, so expressions such as `2 * INGOTS` derive `288` from `GTRecipeBuilder.INGOTS` instead of hard-coded units.

Fluid lowering is still fail-closed: unresolved fluid expressions and linked methods remain explicit `fluids` blockers. The recovery pass also now recognizes explicit `FluidRegistry.getFluidStack(...)` receiver calls, fixing a previously unresolved family, and lowerers report a blocker rather than silently dropping a fluid whose semantic recovery is absent.

Scalar field evaluation was tightened at the same time: Java fields now record `final`, and project constant evaluation follows only `static final` fields (enum constants remain intrinsically fixed). This removes the possibility of folding a mutable static from its initializer.

Full GT5 result:

- direct fluid semantics: **6,291 / 6,582**, up from 6,249 after explicit registry-call recovery;
- linked fluid methods: 208;
- recipes blocked by fluids: **460**, down from 3,558;
- target recipes lowered: **886 / 5,791 (15.30%)**, up from 387 / 5,791 (6.68%);
- debug full-corpus scan after the change: **16.03 s**, ~594% CPU, ~246 MiB RSS on Acer.

The dominant remaining target-content blockers are now item inputs (2,992 recipes), modifiers (2,496), item outputs (2,379), and metadata (1,156). The largest directly understood item family not yet represented in target lowering is material-item access (`MaterialItem`), so item selector normalization is the next content milestone.

### Material item target lowering

Material-backed item accessors now lower to the same source-independent `ItemSelector::MaterialForm` representation used by ore-dictionary forms. Amounts and item metadata use the project scalar evaluator, so statically provable constants no longer block item lowering merely because they are not literals.

The adapter maps only source-backed accessor families. In addition to direct `get(prefix, amount)`, `getPart(...)`, and `getComponentByPrefix(...)`, the GT/GT++ material helpers cover dusts, plates, gears, rods, rings, wires/cables, ores, cells, ingots, nuggets and the other concrete `OrePrefixes` wrappers present in the source. `Materials.getSolid(...)` was corrected to remain a fluid accessor; GT5 defines it as returning `FluidStack`, so treating every material `get*` call as an item accessor would have been unsound.

Full GT5 result after this pass:

- target recipes lowered: **1,268 / 5,791 (21.90%)**, up from 886;
- item-input blockers: **1,945**, down from 2,992;
- item-output blockers: **1,500**, down from 2,379;
- fluid blockers: **457**, down from 460 after recognizing `getSolid`;
- direct fluid semantics: **6,294 / 6,582**;
- modifiers are now the largest blocker family at **2,496**, followed by item inputs (1,945), item outputs (1,500), metadata (1,156), fluids (457), chances (418), and non-constant EU/t (417).

A source census shows the `modifiers` bucket is itself highly skewed: `circuit(...)` accounts for 2,312 call sites, while the remaining modifier methods are individually small. GT5's `GTRecipeBuilder.circuit(int)` materializes `GTUtility.getIntegratedCircuit(config)` into the item-input array, so it should be lowered as explicit recipe-input semantics rather than preserved as a generic opaque modifier. That is the next high-leverage target step.

### Required-versus-consumed inputs and linked item helpers

GT5 encodes catalyst/configuration inputs by constructing an `ItemStack` with `stackSize == 0`. In particular, `GTRecipeBuilder.circuit(int)` calls `GTUtility.getIntegratedCircuit(config)`, which returns `ItemList.Circuit_Integrated.getWithDamage(0, config)`. Carrying that sentinel convention into the target engine would make a source-runtime accident part of the new recipe model, so target input IR now separates the amount required for matching from whether that amount is consumed:

- `ItemInputStackSpec.amount` is the required count;
- `ItemInputStackSpec.consumption_probability` records the probability that a matched input is removed;
- ordinary positive source stack sizes default to exact probability 1;
- a GT source input with stack size zero becomes required amount 1 with exact probability 0.

This also makes `circuit(...)` ordinary target input semantics instead of an opaque recipe modifier. `itemInputsUnsafe(...)` is likewise no longer a modifier: the GT5 source differs only by allowing stack sizes greater than 64, while target quantities are already represented as `u64`.

The same pass lowers statically identifiable `GTModHandler.getModItem(...)` and `getIC2Item(...)` calls to named target items, including amount and metadata. Overloads carrying a non-null replacement stack remain fail-closed because the fallback changes identity semantics; literal-null replacement overloads are equivalent to having no fallback and can lower safely.

Project-linked item methods now retain the original receiver expression as well as its inferred type. This allows concrete wrapper identities such as `ItemRefer.Radiation_Protection_Plate.get(2)` to remain distinguishable, while calls on a merely typed local such as `Werkstoff w` remain unresolved. Source-backed linked adapters currently cover:

- `goodgenerator.util.ItemRefer#get(int)` for concrete `ItemRefer.*` receivers;
- `gregtech.api.enums.ItemList#get(long,Object...)` for concrete `ItemList.*` receivers;
- `ComponentAssemblyLineLoader#get(OrePrefixes,Object,int)` when both prefix and material arguments resolve to qualified source identities.

Direct GT++ material recognition also includes the `MaterialsElements`, `MaterialsOres`, and `MaterialsNuclides` families. A project-enrichment pass now revisits nested `copyAmount*`/ore-unification wrappers after linking so an outer direct wrapper cannot permanently hide an inner project-resolvable item. That enrichment is structurally useful but did not itself increase fully lowered recipe count on the current corpus, indicating that the remaining such wrappers predominantly contain genuinely dynamic values/helpers.

- item-input blockers: **1,403**, down from 1,945;
- item-output blockers: **1,126**, down from 1,500;
- metadata blockers: **1,156**;
- fluid blockers: **457**;
- chance blockers: **418**;
- non-constant EU/t blockers: **417**;

The largest single gain is circuit normalization: before `itemInputsUnsafe` cleanup and registry-item/helper lowering, the circuit pass alone raised fully lowered recipes from 1,268 to 2,492 and collapsed modifier blockers from 2,496 to 286. `itemInputsUnsafe` then reduced modifier blockers to 178 without changing complete-recipe count, showing those recipes had independent blockers. Registry item lowering raised complete recipes to 2,807; receiver-aware linked helpers then reached 2,911.

Item inputs/outputs remain large, but metadata is now comparable in scale and contains real machine behavior (`COIL_HEAT`, `SCANNING`, research/fuel/casing requirements). Generic metadata must not be discarded merely to improve coverage. Output/input chance arrays are smaller but structurally clean core recipe semantics and are a good candidate for a dedicated target-IR pass after the next item-helper census.


### Exact item consumption and production probabilities

GT5's recipe chance arrays are now lowered as behavior rather than left as an opaque blocker. Source inspection confirms that GT uses an integer scale of 1–10,000 where 10,000 is 100%, but that source convention does not leak into core content. `minecraft-redox-core` now represents probabilities as exact reduced rationals (`Probability { numerator, denominator }`), so `2500/10000` becomes `1/4` and `1250/10000` becomes `1/8`.

The target semantics distinguish matching from stochastic execution:

- item inputs are always required for recipe matching; `consumption_probability` controls whether a matched quantity is consumed;
- item outputs carry `production_probability`;
- zero-stack GT catalyst/configuration inputs remain required amount 1 with consumption probability 0, regardless of a source chance entry;
- absent chance arrays mean exact probability 1;
- GT's runtime behavior for a chance array shorter than the final slot array is preserved by defaulting trailing entries to probability 1. This matters for the two corpus `inputChances(...)` recipes, which append an integrated circuit after setting the chance array;
- dynamic, out-of-range, or oversized chance arrays remain fail-closed `chances` blockers.

The only two direct `inputChances(...)` call sites in the current GT5 corpus each have one ordinary input plus a subsequently appended circuit, so GT's runtime merging of identical item-input types does not introduce a hidden correlation mismatch in the chance-bearing input corpus. There are 427 direct `outputChances(...)` sites. No direct `fluidInputChances(...)` or `fluidOutputChances(...)` call sites were found, so fluid probability IR is intentionally deferred until source evidence requires it.

Full GT5 result after this pass:

- target recipes lowered: **3,064 / 5,791 (52.91%)**, up from 2,911 / 5,791 (50.27%);
- chance blockers: **50**, down from 418;
- item-input blockers: **1,403**;
- metadata blockers: **1,156**;
- item-output blockers: **1,126**;
- fluid blockers: **457**;
- non-constant EU/t blockers: **417**;
- modifier blockers: **178**.

The remaining chance tail is now too small to justify chance-specific overfitting. The next pass should return to the large semantic blocker families: concrete item helpers/selectors and typed machine metadata.


### Typed minimum process heat requirement

`GTRecipeConstants.COIL_HEAT` is now lowered as source-independent machine behavior rather than retained as opaque metadata or GT's legacy `mSpecialValue` alias. GT5 declares the key as the required heating-coil heat in Kelvin, and its Electric Blast Furnace, Plasma Forge, and Exothermic Hearth consumers use the same value both to reject recipes above machine heat capacity and as the recipe-heat input to heat overclock/discount calculations.

Core recipe IR now carries typed `RecipeRequirement` values; the first variant is `MinimumHeat { kelvin }`. Builder-call recovery retains parsed argument expressions so metadata values can use the same project-backed scalar evaluator as amounts, EU/t and probabilities. Repeated `COIL_HEAT` entries preserve GT metadata storage's `Map.put` last-write-wins behavior. All unknown metadata keys and non-static/non-negative heat values remain fail-closed metadata blockers; no generic Java metadata bag is copied into the target runtime.

### Named minimum machine capabilities

Three casing-tier metadata families are now normalized into a generic source-independent recipe requirement: `MinimumCapability { capability, level }`. Source/runtime inspection proves that all three are threshold checks against a machine capability, even though their internal block-tier offsets differ:

- `COAL_CASING_TIER` -> `machine_capability.component_assembly_line_casing`; the Component Assembly Line requires `recipe level <= casingTier + 1` and also uses surplus capability levels to reduce duration by powers of two;
- `CHEMPLANT_CASING_TIER` -> `machine_capability.chemical_plant_solid_casing`; the Chemical Plant requires `recipe level <= mSolidCasingTier`;
- `PRECISE_ASSEMBLER_CASING_TIER` -> `machine_capability.precise_assembler_casing`; Precise mode requires `recipe level <= casingTier + 1`.

The target requirement stores the normalized capability level that recipe execution compares against, not source block metadata or source field names. This leaves machine-specific policy such as the Component Assembly Line's surplus-tier speed bonus in the machine executor while making the recipe requirement reusable.

`ALGAE_POND_TIER` is explicitly *not* lowered into this family. The Algae Pond searches for a recipe whose legacy special value equals the current pond tier; that is exact variant selection, not a minimum capability threshold. A characterization test protects this distinction. As with heat metadata, repeated values for the same capability inherit GT metadata storage's last-write-wins behavior.

### Semantic named item variants

Target item identity now has a source-independent named-subtype form, `ItemSelector::NamedVariant { id, variant }`, for content whose legacy runtime representation is one base item plus a metadata/damage subtype but whose *semantic* subtype already has a stable name. This avoids reverse-engineering and preserving arbitrary Minecraft metadata integers when the source exposes a stronger identity.

Source-backed adapters currently cover only transparent families whose constructor behavior was inspected:

- GregTech bee combs: concrete `ItemComb.getStackForType(CombType, amount)` lowers as the concrete comb item plus named `CombType` subtype;
- GT++ base particles: `Particle.getBaseParticle(Particle[, amount])` lowers as the standard particle base item plus named `Particle` subtype;
- GT++ comb enum instances: concrete `GTPPCombType.X.getStackForType(amount)` lowers as the GT++ comb item plus named enum subtype;
- KekzTech crafting components: `getStackOfAmountFromDamage(Items.X.getMetaID(), amount)` lowers as the crafting-component item plus named `kekztech.Items.X` subtype rather than the numeric meta ID.

Dynamic comb receivers remain blocked. GT++ `Particle.getIon(...)` is deliberately excluded because it writes ion charge into NBT; representing it faithfully requires structured item state rather than a subtype selector. BartWorks `BioCulture`/`BioData` helpers are likewise excluded because their payloads are mutable biological state and can carry plasmid/data rather than a simple enum subtype.

### Assembly Line research as target recipe unlocks

GregTech Assembly Line `RESEARCH_ITEM` plus `SCANNING` metadata is now lowered as a source-independent `RecipeUnlock::Scan` rather than preserved as metadata or expanded into source fake recipes. The target unlock carries the research sample, scan duration in ticks, and EU/t. The sample is represented as a required input with deterministic consumption, matching `ScannerHandlerLoader`/`MTEScanner`, where `mResearchItem.stackSize` is removed when research begins.

The source data-stick output, persistent recipe hash, `specialValue(-201)`, scanner fake recipe, and assembly-line visual recipe are intentionally not part of the target semantic model. They are GregTech UI/transport machinery around the fact that completing the scan grants access to the Assembly Line recipe.

Metadata item values reuse the normal project-aware item recovery/lowering path. `BuilderCall` therefore retains source byte positions, allowing research samples such as linked `ItemRefer.*.get(...)` helpers to resolve with the same provenance rules as ordinary recipe items rather than creating a weaker metadata-specific parser.

Corpus characterization found 142 Assembly Line recipes carrying `SCANNING`: 134 also have `RESEARCH_ITEM`, while eight have scanning data alone. GregTech's `AssemblyLine` recipe-map transformer returns no recipe when `RESEARCH_ITEM` is absent, so those eight remain fail-closed instead of being invented as usable target recipes. Missing or non-positive scan time/EU/t is likewise not accepted as a usable target unlock.

This removes metadata as a blocker from 126 recipes and adds 32 fully lowered recipes.
